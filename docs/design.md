# erp/credit 的设计

本页写这个组件为什么这样设计：术语、拥有的数据、规则、命令与事件、依赖、实现状态与未决问题。写给要修改它的人与 AI。怎样使用、部署与配置在 `BRICKKIT.md`；代码在哪、怎样构建与测试在 `AGENTS.md`。跨组件的规则在装配项目：预占分支的状态、命令与恢复在协议 04（本组件是参与方），订单占用怎样转为应收占用、应收事实的乱序在协议 05 的“应收形成与信用占用的转换”，期初在协议 16。规则少，只有这一份文档。

## 边界

对客户做信用控制：额度、信用占用与超限判断。

| 不在这里 | 归谁 |
| --- | --- |
| 应收未清项、核销 | `erp/finance`（本组件只按它的应收事实增减占用） |
| 订单与确认过程 | `erp/sales`（预占的协调者） |
| 伙伴本身、客户角色 | `mdm/partner` |
| 临时额度的审批任务 | 本组件的审批流程；统一待办入口在 `infra/workflow`（下游，以后） |

## 术语

| 业务叫法 | 定义 | 代码标识符 |
| --- | --- | --- |
| 额度 | 一个客户在一个法人、一种币种下可以占用的上限；订单只占同币种的额度，不换算 | `credit_limit`：（`partner_id`、`legal_entity_id`、`currency`） |
| 信用政策 | 法人对“没有该币种额度的客户”的处理：`block`（拒绝）或 `unlimited`（不控制，照样记占用）；以后加评分与审批规则 | `credit_policy` |
| 订单占用 | `held` 与 `committed` 分支未消耗的金额 | `order_exposure` |
| 应收占用 | 按账单身份记的未结清应收（以后，协议 05） | `receivable_exposure` |
| 已用、可用 | 已用 = 订单占用 + 应收占用；可用 = 额度 − 已用 | `used`、`available` |
| 超限 | 预占的金额大于可用，预占被拒绝 | `over_limit` |
| 预占分支 | 一张订单一次确认在本组件的一条分支，金额是订单含税总额、订单币种（协议 04） | `branch`；状态同协议 04 |
| 临时额度、例外放行 | 超限后经本组件的审批放宽，用户再重新确认订单（以后） | — |

## 拥有的数据

| 表 | 内容 | 终态与保留 |
| --- | --- | --- |
| `credit_policy` | 每个法人一行：没有额度时的处理 | 随法人存在 |
| `credit_limit` | 额度：伙伴、法人、币种、金额、状态（`active`、`suspended`）、订单占用、应收占用、版本；加锁的对象 | 停用，不删除 |
| `branch` | 预占分支：分支身份、额度行、金额、已消耗、状态、暂存期限、修订、拒绝原因；墓碑也是分支行 | 终态保留，作幂等与墓碑的依据 |
| `consumption` | 消耗记录（消耗身份 → 分支、金额） | 永久 |

以后还有：按账单身份的应收占用与暂存的应收事实（协议 05 第 5 步）、临时额度与审批记录、事实去重的收件表。

## 规则

- **不超限**：已用 ≤ 额度。每个改变占用的命令先锁 `credit_limit` 行，在锁内裁决。一条分支只涉及一个额度行，所以没有多行加锁顺序的问题。
- **没有额度行**：按法人的 `credit_policy`：`block` 时预占被拒绝（原因“没有信用额度”）；`unlimited` 时建一条金额为空（不控制）的额度行再占用，占用照样记，以后设了额度立即生效。法人没有政策行时按 `block`。
- **额度停用**（`suspended`）：新的预占一律拒绝；已有的分支照常确认、取消、消耗。
- **改小额度**：可以改到低于已用，不拒绝；只影响之后的预占（之前的占用不追溯）。
- 分支的状态迁移、幂等（同身份同金额返回已有结果，不同金额冲突拒绝）、墓碑、暂存期限、“已到期不能确认复活”、“确认占用没有自动到期”全部照协议 04 的状态迁移表。

每个命令改什么：

| 命令 | 检查 | 写 | 拒绝时 |
| --- | --- | --- | --- |
| 预占（新分支） | 额度行 `active`；`金额 ≤ 可用`（不控制时跳过） | 分支 `held`；`order_exposure += 金额` | 分支 `rejected`，原因 `over_limit`、`no_limit`、`limit_suspended`；发布超限事件（只对 `over_limit`）；占用不变 |
| 预占（分支已在） | 内容相同？ | — | 不同：冲突；相同：返回已有状态（含墓碑） |
| 确认 | `held` 且未到期 | `committed` | 返回该状态，不复活 |
| 取消（分支已在） | `held` 或 `committed` | `released`；`order_exposure −= 未消耗的金额` | 终态：返回该状态 |
| 取消（分支不在） | — | `cancelled` 墓碑 | — |
| 暂存到期（工作项） | 仍是 `held` 且已过期限 | `expired`；释放占用 | 已被确认或取消：不动 |
| 消耗 | 分支 `committed`；金额 ≤ 剩余 | `order_exposure −= 金额`（以后同一事务 `receivable_exposure += 金额`，协议 05） | 消耗身份已用过：同内容返回原结果，不同内容冲突 |

| 临时额度与例外放行的申请与审批 | 用户面 | 以后 |

用户面的资源带法人维度（值集合）。额度的维护以后要求业务确认（受保护的操作，安全 08）；本版只靠操作权限。

## 事件

流 `erp.credit`：

- 额度状态：可覆盖的完整状态事件（额度、订单占用、应收占用、可用、状态、版本），每次占用变化都发，供销售显示与报表。
- 超限：预占因超限被拒绝时发一条（伙伴、法人、币种、请求金额、可用）；通知组件可以订阅提醒信用经理。
- 预占分支的状态：可覆盖的状态事件。

## 依赖

- `mdm/partner`（必需）：建立额度时问资格（用途 `sell`：伙伴与该法人的客户角色都 `active`）；不是资格的不建。
- `mdm/org`（必需）：建立额度与政策时，法人存在且启用（来源读取）。
- `mdm/currency`（必需）：币种存在且启用。
- 身份、授权（必需）；`infra/audit`（可选）。
- `erp/billing`（可选，以后）：订阅“已出账”，消耗订单分支、增加应收占用；缺时订单占用不转换，订单完成或关闭时由销售释放剩余分支，并在额度上注明“只按订单占用”。
- `erp/finance`（可选，以后）：订阅应收结清、减少、重开；缺时应收占用只增不减，需要人工释放。

下游：`erp/sales`（协调者）；`infra/workflow`（以后，临时额度的审批，缺时在本组件页面处理）。

## 实现状态

实验第 7 步：信用政策、额度的维护、预占分支的预占、确认、取消、查询、消耗、可用额度查询、额度与分支的状态事件、超限事件。答“能力不支持”的：应收占用与它的转换（订阅已出账与应收事实）、临时额度与例外放行、分支的调整、期初。

所以本版的信用只按订单占用控制：出账之后占用仍记在订单分支上，订单完成或关闭时销售释放剩余分支，已出账未收款的部分不再占用额度。这是边界卡写明的“缺出账时”的降级，在额度事件里带 `receivables_tracked: false` 标明。

## 部署与替换

低到中负载；适合外壳。信用评分与审批规则是替换点；整体可替换（另一实现提供同形的 `ReservationService` 与事件）。适用协议 01、02、04、05、13、16、安全 01–09。

## 未决问题

- 订单占用的金额是否含税：本版按订单含税合计（客户欠的是含税金额）；税率本版由人录入（销售的定价规则）。
- 多币种客户的合并控制（按法人本位币折算总额）：协议 04 待定，本版按币种分开。
